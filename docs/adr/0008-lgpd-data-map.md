# LGPD data map: what Feudo stores, why, for how long, and how it is protected

Feudo is a data controller under LGPD regardless of being free or small, and it processes the most sensitive category of personal data an ordinary person has: their bank movements and the secret that grants access to them. We therefore fix the data map up front, minimize by default, and make export and deletion first-class flows. These ship before registration opens beyond the owner's household; the registration mode `open` (resolved as in ADR-0001) is blocked until they do (together with ADR-0005 step 3).

## Principles

- Terms of use and privacy policy are accepted at registration, with the version and timestamp recorded.
- An explicit consent step precedes any bank connection, explaining what is read and that credentials can be revoked at any time.
- We store only what the ledger, reserve and analyses need. No CPF in clear anywhere; provider credentials encrypted at rest; audit log without financial content.

## Rights and flows

- **Export**: a user can download everything Feudo holds about them (identity, memberships, connections metadata, their accounts and transactions, annotations they made) in a machine-readable file.
- **User deletion**: soft delete immediately (account hidden, sessions revoked, sync stopped, provider credentials destroyed at once), hard delete after a 7-day grace during which the user can cancel. A user who cancels re-enters their credentials; nobody who asked to leave has their bank read for seven more days. Hard delete removes the user, their connections, accounts and transactions from every household they belong to; before confirming, the members of those households are told which months lose data. If the user is an owner, ownership passes per ADR-0001.
- **Household deletion**: same 7-day grace as user deletion (household hidden to all members, reversible by the owner), then hard delete of memberships, annotations, analyses and everything assigned to the household; bank connections survive with their users and their accounts become unassigned.
- **Credential removal**: a user can delete their provider credentials at any time; sync stops immediately and the credentials are destroyed, while already-synced data stays until the connection or user is deleted.

## Consequences

- The keyed-hash secret and the credentials encryption key are two different secrets; losing the encryption key means users must re-enter credentials, losing the hash key means re-hashing on next sync. Neither loss exposes data.
- Every table added later must be placed in this map in the same PR; the `reviewer-security` lens checks for it.
- Any third party that receives personal data (Resend for email, Anthropic for analyses, Pluggy for bank access, Neon and Vercel for hosting) is named in the privacy policy; analyses send computed numbers only, never transactions.
- The `feudo-preview` Neon project (used by Vercel Preview/Development and by CI) never holds production personal data: it is a separate project from production, not a copy or a restore target, so there is no path by which production data reaches it.
- Consent fields (`user.terms_version`, `user.terms_accepted_at`) are immutable after sign-up: `hooks.before` rejects any `/update-user` request that carries either field, so a signed-in session can never rewrite its own consent record without a fresh acceptance flow (#25).

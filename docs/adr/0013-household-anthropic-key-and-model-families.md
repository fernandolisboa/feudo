# The household brings its own Anthropic key and picks a model family per reading kind

ADR-0004 fixed the AI layer's contract (numbers in, interpretation out) but ran every household's analyst on one deploy-wide `ANTHROPIC_API_KEY`, with Sonnet fixed for on-demand readings and Opus fixed for the monthly one. That does not scale past the owner's household: usage, billing and the choice of model should belong to the household paying for its own readings, not to whoever holds the deploy's key.

## Decision

- **The key belongs to the household, not the deploy or a user.** `household_ai_settings` (ADR-0001: household-scoped, `household_id` the primary key, cascading with the household) holds the household's own Anthropic API key, encrypted the same way as Meu Pluggy credentials (AES-256-GCM, `platform/crypto.ts`, moved there from `sync/` since both `sync` and `analysis` need it and a slice must not reach into another's internals), plus the model family chosen for the monthly reading and for the on-demand one, and who last changed any of it. Only an owner or admin can register, change or remove the key or the families (`canManageHouseholdSettings`); every member sees the current state (whether a key is registered, by its last 4 characters only, and the two families) on Casa. The key is never sent back to the browser, never logged, and never appears in an error message or an audit entry. `crypto.ts`'s AES key is derived with a `purpose` string specific to each caller (ADR-0011's 2026-10-16 amendment): Meu Pluggy credentials keep `"feudo:provider-credentials"`, the household's Anthropic key gets its own, `"feudo:household-ai-key"`, so the same `ENCRYPTION_KEY` can never open one slice's ciphertext as if it were the other's, even by a copy-paste mistake between them. `householdHasUsableKey` is the one predicate for "this household's analyst can run": a ciphertext this deploy's `ENCRYPTION_KEY` cannot open (a rotated key, a tampered row) counts as no key everywhere it is checked — the Visão geral/Reserva/Análises gate, Casa's own key line, the save and remove actions, and the cron — never shown as a working key that silently stopped decrypting.
- **A key is verified before it is ever stored, and verification itself is rate-limited.** Saving calls Anthropic's Models API (`client.models.list({ limit: 1 })`); 401/403 means the key is invalid, anything else unreachable means "could not verify now, try again". An unverified key is never written. Before that call, `ai_key_verification_attempt` (household- and user-scoped, ADR-0001) caps attempts at 5 per household per rolling hour and 10 per submitting member per rolling day, whichever is hit first; a capped attempt returns `rate_limited` without ever calling Anthropic and without writing a row, so it costs the household nothing. The two limits share one table and one `reserve` transaction (locking the household's row, then the submitting member's own, in that order, the same lock ordering `manual_sync_trigger` and `recordAccessWithinQuota` already use), and each household's own write opportunistically deletes that household's rows older than the wider of the two windows, so the table never needs a separate prune job.
- **The family is chosen; the version is resolved.** The household picks Haiku, Sonnet or Opus per reading kind (Opus monthly, Sonnet on-demand by default) and never pins a version. At call time, `resolveModel(family, tier)` lists the household's available models, keeps the ids that start with `claude-<family>-`, whose capabilities support structured outputs and the tier's effort level, and picks the newest by `created_at`. A listing failure or nothing qualifying falls back to a pinned, known-good id per family (`claude-haiku-5-5`, `claude-sonnet-5-5`, `claude-opus-5-5`). If a freshly resolved id differs from the pinned one and the completion call itself is rejected (`BadRequestError` or `NotFoundError`), the call retries once on the pinned id, logging only the model id that failed. Effort still follows the reading's depth (medium for on-demand, high for monthly), never the family; the server-side fallback beta (`betas: ["server-side-fallback-2026-07-01"]`, `fallbacks: "default"`) is sent for Sonnet and Opus but never for Haiku, which has no fallback tier to fall back to. The resolved id is stored as `requested_model` before the call, same as before; the answering id (which may differ, after a fallback or a pinned retry) is stored as `model`.
- **The deploy-wide switch narrows to "is Anthropic allowed at all".** `AI_PROVIDER` stays `anthropic`, `fake` or `off`; unset now means `anthropic`, which only needs `ENCRYPTION_KEY` to exist (nothing could open a stored key without it, so its absence is treated as `off`). `ANTHROPIC_API_KEY` is retired. `isAnalysisEnabled` became per-household: with `anthropic`, a household with no key registered is off, same as if the deploy switch were off, while a household that has registered one gets its analyst; `fake` stays on for every household regardless of a key, since it ignores keys entirely, and is still refused in production; `off` is off for everyone. Visão geral and Reserva hide the panel exactly as before; Análises explains that an owner or admin registers a key on Casa, with a link there. The monthly cron builds a client per household from that household's own key and counts a keyless household as skipped, never failed; the on-demand action returns `disabled` for one.
- **A provider seam separates "can Anthropic run at all" from "with which household's key".** `AiProvider` exposes `verifyKey(apiKey)` and `clientFor(apiKey | null)`; the fake provider's `verifyKey` accepts any non-blank key and its `clientFor` ignores whatever key it is given, so previews and e2e keep working with no key registered anywhere.
- **Export, narrowly.** The per-user data export otherwise excludes household-wide settings (CONTEXT.md, ADR-0008), but a household's chosen families and whether it has a key export too, to whoever last changed them (`updated_by_user_id = session.userId`, the same authored-by filter the export already applies to categorization rules and reserve marks) — never the key or its ciphertext. This keeps the export's existing invariant (a user's own file never carries something only because they happen to be in the household) while still answering "what did I set" for the one piece of household state this person is responsible for.

## Consequences

- A household that never registers a key simply has no analyst, with no server-wide fallback to fall back to; this is a deliberate product choice (CLAUDE.md: "the household brings its own Anthropic API key"), not an outage.
- A new Anthropic model release can change a reading's cost, latency or behaviour without a deploy, since the newest qualifying version of the chosen family is picked at call time; every reading still records exactly which id answered it, so a change is visible after the fact even though it was never pinned ahead of it.
- The pinned ids are a safety net the code must keep current by hand as Anthropic retires old families; letting them go stale only ever falls further back to a model that still exists today, never forward to a broken one.
- Moving `sync/crypto.ts` to `platform/crypto.ts` has no behavioural effect on existing ciphertext; a stored Meu Pluggy credential still decrypts under `"feudo:provider-credentials"` exactly as before, and it only lets a second slice depend on it without reaching into `sync`'s internals (ADR-0011). `platform/encryption-key.ts` became the one place that reads and validates `ENCRYPTION_KEY` (≥ 32 characters), used by both `sync/env.ts` and `analysis/env.ts`, so a short or blank key is treated as absent the same way in both and `readAiProviderName` can never tell a caller `anthropic` is on when nothing could actually decrypt a key for it.
- A verification attempt (an API call, and the quota row it costs if under the limit) is spent whether the key turns out valid or not; only a never-attempted household, one that never submits a key at all, spends nothing.

## Amendment 2026-10-22 (issue #125)

Every ciphertext `platform/crypto.ts` writes is now an `enc:v2` envelope bound to its row's owner: the household id for this key, the user id for Meu Pluggy credentials, passed as AES-GCM additional authenticated data, with the tag length pinned to 16 bytes on both sides. A key copied from one household's row into another's fails to decrypt there and counts as no key (`householdHasUsableKey`). `enc:v1` envelopes written before the change still open; the household's key is rewritten as `v2` the first time a reading decrypts it (`rebindLegacyApiKey`, conditional on the old ciphertext so it never overwrites a key saved in the meantime); Meu Pluggy credentials the same way on any sync that reads them.

The `v1` read path is a window, not a permanent mode: rows nothing reads (a household that never runs a reading, credentials with no connection left) stay `v1` and movable between owners until rewritten. Accepted for that window, which closes by 2026-11-30: issue #152 sweeps every remaining `enc:v1:%` row and then removes the legacy branch from `decryptSecret`. The daily cron steps `sweepLegacyCredentials` and `sweepLegacyApiKeys` now rewrite those unread `v1` rows (#152); the legacy branch is removed once production shows `remaining=0` for both.

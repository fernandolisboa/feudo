# Better Auth for identity; the household is the tenant

Feudo needs multi-tenant identity from day one (strangers register, invite partners, and one person can sit in more than one household), and a solo project cannot afford to hand-roll sessions, verification, password reset and invitations securely. We use Better Auth with its `organization` plugin as the identity and membership engine, mapped onto Feudo's vocabulary (organization → household, member → membership, invitation → invite), and we treat the household as the tenant that scopes every piece of financial data.

## Decision

**Identity (Better Auth, Drizzle adapter on Neon Postgres, emails through a selectable `EmailSender`)**

- Every auth email (verification, magic link, password reset, invitation) goes through one `EmailSender` chosen by `EMAIL_PROVIDER`: `resend` (the default) or `smtp`, any authenticated SMTP relay. SMTP was added (2026-09-21) because Resend only delivers to arbitrary recipients from a verified domain and the first household has none; a relay such as a Gmail account with an app password fills that gap without a domain purchase. `fake` (messages stored in `fake_sent_emails`) exists for preview, CI and E2E only and is refused in production by `readEmailProvider` (ADR-0008). Whichever provider production runs is a personal-data processor and must be named in the privacy policy (ADR-0008).

- Email + password with mandatory email verification (`requireEmailVerification`), magic link (`magicLink` plugin) and password reset. Magic-link and reset links are single-use and short-lived (plugin defaults: 5 minutes for magic links, 1 hour for reset). Email verification links are signed, expiring tokens (1 hour, `emailVerification.expiresIn`) that no-op on re-use instead of erroring, so a user who clicks an old email or double-clicks a link is never shown a broken page.
- Better Auth's built-in rate limiter, stored in the database (in-memory storage does not survive Vercel's serverless invocations), with the default strict rules on sign-in, sign-up, verification and reset endpoints. Two endpoints Better Auth's own defaults don't cover — magic-link sign-in and the password-reset submission — get an explicit `rateLimit.customRules` entry in `options.ts` at the same 10s/3 strictness; the GET links those two flows email out (`/magic-link/verify`, `/reset-password/:token`) get their own, looser explicit rule instead, since a 429 on a browser-navigated GET has no route handler to turn it into a friendly page. Feudo adds its own limits on sync and AI endpoints (see ADR-0005 and ADR-0004).
- The registration mode (`open|invite|closed`) is read at request time, first from the `registration_mode` item of the Vercel Global Config store connected to the deployment (`GLOBAL_CONFIG`), then from the `REGISTRATION_MODE` environment variable, defaulting to `invite`; the store exists so the mode can change without a redeploy, and an unreachable or invalid store value falls back to the environment (never opens registration by accident). `closed` disables sign-up entirely; `invite` allows sign-up only for an email that holds a pending invite; `open` is the product default but stays blocked until the gates in ADR-0005 and ADR-0008 are cleared.
- Better Auth's tables are generated by its CLI and migrated with drizzle-kit like every other table. Only the `auth` and `households` modules touch Better Auth; the rest of the code sees a session with `userId` and `householdId`.

**Tenancy (household)**

- A user can belong to several households and works in exactly one at a time, the active household, stored on the session (`activeOrganizationId`). Every server action and route handler takes the household from the session, never from the request body or URL, with one deliberate exception: switching which household is active takes the target household id from the client, because that is the action's whole purpose, but the switch itself is only ever applied after the server re-checks that the session's user actually has a membership row in that household — the id is never trusted on its own.
- Roles: `owner` (exactly one per household; only role that transfers ownership or deletes the household), `admin` (manages people and settings), `member` (manages only their own bank connections). Better Auth allows several owners; Feudo does not. The `households` module refuses to invite or promote someone to `owner`; ownership changes only through a dedicated transfer action that promotes the new owner and demotes the old one in one database transaction. Enforced with three lines of defense: `organizationHooks.beforeUpdateMemberRole` (`apps/web/src/modules/auth/options.ts`) rejects any role update to `owner` outright; a partial unique index on `member (organization_id) where role = 'owner'` makes a second owner row impossible even if that hook is ever bypassed; and a deferred constraint trigger, `member_single_owner_trigger` (`0007_single_owner_trigger.sql`), asserts at commit that every organization with at least one member has exactly one owner. The unique index only ever catches a _second_ owner row; it never catches a _zero_-owner state, which is exactly what Better Auth's own `/organization/leave` and `/organization/remove-member` endpoints can produce: both read the target member's role with a plain, unlocked `SELECT` and only take a row lock on the `DELETE` that follows, so a `transferOwnership` that promotes that same member to owner and commits in the gap between that read and that delete leaves the delete removing the household's new (and only) owner. The trigger closes that window at the database level, for every write path to `member`, including a raw call to either endpoint — not just the ones `households.transferOwnership`'s own `for update` lock protects. The migration installing the trigger (`0007_single_owner_trigger.sql`) opens with a pre-check that fails the migration outright if any existing household already violates the invariant, rather than installing a trigger that would then block every future write to that household's members; recovery is a manual promotion (docs/runbooks/households.md, "Single-owner enforcement").
- Transferring ownership always demotes the previous owner to `admin` in the same transaction that promotes the new one — a household never has a former owner without a role, and the demoted owner keeps managing people and settings instead of being pushed down to `member`.
- Invites are sent by email with a role, expire after 24 hours (`invitationExpiresIn`, overriding the plugin's 48-hour default) and can be cancelled by the inviter or any admin/owner. `invitation.delivery_failed_at` and `invitation.last_sent_at` (`0008_invitation_delivery_failed_at.sql`) are Feudo-owned columns grafted onto Better Auth's own `invitation` table, the same pattern as `user.theme` (ADR-0010): written only by `sendInvitationEmail` (`auth/options.ts`, on every send attempt — initial and resend — success or failure) and read household-scoped (`households.listPendingInvitations`, `households.resendInvitation`), never exposed to another household's session.
- The raw `/organization/list-invitations` and `/organization/get-full-organization` endpoints return every pending invitee's email to any member of the organization, not just the people who can manage invites (Better Auth 1.7.3 has no `organizationHooks` entry point for either). `auth/options.ts`'s global `hooks.before` restricts both to `owner`/`admin`, resolving the target organization the same way each endpoint's own handler does (query id, or — for `get-full-organization` — query slug first, or the session's active household), so the guard can never be bypassed by an empty or missing query parameter the endpoint itself would still resolve.
- When an owner deletes their user account, ownership passes automatically to the oldest admin, otherwise the oldest member, after the owner has been warned. When the last member leaves, the household is deleted (see ADR-0008 for what that removes). Not yet implemented (#26): that succession and the owner's own `member` row deletion must run inside the same transaction that removes the user, promoting the successor before demoting/deleting the departing owner — `member_single_owner_trigger` above is deferred to commit, so a transaction that reaches a valid final state is fine, but a delete that leaves the household ownerless past commit is rejected regardless of intent.

**Data scoping: two scopes, not one**

Every domain table is scoped in one of two ways, and each table declares which:

| scope     | tables (initial)                                                                                                                                                                                | key            | who can reach it                                            |
| --------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------- | ----------------------------------------------------------- |
| user      | bank connection, provider credentials                                                                                                                                                           | `user_id`      | only the owning user, in any of their households            |
| household | `household_settings` (name lives on `organization`; time zone, reserve multiple), account assignment (investment positions are accounts), transactions, categorization, reserve marks, analyses | `household_id` | every member of that household, through scoped repositories |

`household_settings.household_id` references the plugin's own `organization.id`, so the household's
identity row (`organization`, plus `member` and `invitation`) is Better Auth-owned and generated by
its CLI, while everything Feudo adds about a household — starting with `household_settings` in this
ticket — is a normal Feudo table carrying `household_id` and going through
`households.householdScope(session)` and a scoped repository like every other household table.

Bank connections belong to the user who authorized them, never to a household. Each synced account is assigned to exactly one household at a time (default: the user's active household at connection time) and can be moved by its owning user; an account whose household was deleted becomes unassigned and is visible only to its owner until reassigned. Synced transactions are stored once per account and carry the account's current `household_id` so repositories can scope them; moving an account rewrites that column for the account and its transactions in one database transaction.

Repositories are constructed with the household (or user) taken from the session; no repository method accepts a household id as a parameter. Every new table ships with an isolation test proving household A cannot read, write or trigger jobs for household B.

## Considered options

- **Auth.js / NextAuth**: mature, but organizations, invitations and magic links are all custom code there. Rejected.
- **Clerk / WorkOS**: hosted, good organizations support, but paid beyond small tiers, stores user data outside Brazil-controllable infrastructure and adds a vendor to the LGPD map. Rejected for a free-tier, LGPD-sensitive project.
- **Own membership tables next to Better Auth core (no organization plugin)**: more control, but re-implements invitations, active-organization sessions and role checks that the plugin already tests. Rejected; we accept the plugin's schema and enforce Feudo's stricter rules (single owner, 24h invites, ownership succession) on top.

## Consequences

- Better Auth's vocabulary (organization, member) appears in generated tables and plugin calls only; code, docs and UI use household, membership, invite (see `UBIQUITOUS_LANGUAGE.md`).
- "Every domain table carries `household_id`" (CLAUDE.md) is refined here: user-scoped tables carry `user_id` instead, and an account's `household_id` is nullable only to represent "unassigned". No other nullable tenant key is allowed.
- Moving an account between households carries its transactions' manual categorizations and internal-transfer marks along: they are facts about the transactions, not secrets of the source household. The source household's categorization rules do not move; only what they already applied does. Internal-transfer pairs whose other account stays behind are unpaired in the destination.

# Bank profiles are versioned reference data in the repository, curated by the product

Banking intelligence scores institutions on evidence that changes slowly and must be reviewable, so bank profiles are product-curated reference data, not household data: a versioned data file in the repository, changed only through pull requests with cited sources. They move to a database table only when someone has to edit them without a pull request.

## Decision

- Scope: Nubank, Inter, Itaú, Bradesco, Banco do Brasil, Caixa, Santander, C6, BTG, XP, Sicoob, PicPay, Mercado Pago initially.
- Criteria, each scored as an integer from 0 to 100 (amended 2026-10-02, #21; it was 0 to 5, which left too little range to compare thirteen banks) with cited evidence and a `reviewedAt` date: card benefits, investment access, app and tech quality, security, fees, lock-in, public customer reviews (Reclame Aqui, consumidor.gov.br). Every criterion reads "higher is better for the household": lock-in 100 means the easiest bank to leave. A criterion without a citable source is recorded as insufficient evidence, never given a guessed score. The data file is validated by a Zod schema in CI; a profile with a missing citation fails the build; CI reports stale profiles (`reviewedAt` older than a threshold set in the schema) and the UI shows the review date.
- Weights are household data: the product ships defaults, each household adjusts its own. Scoring is a pure function in `packages/core` over profiles and weights; criteria and default weights are data, not code branches.
- Output of a bank comparison: up to three candidate institutions (amended 2026-10-02, #23; see below) with pros and cons against the institutions the household already uses. The AI layer (ADR-0004) may phrase the reasoning; the ranking and scores come from the deterministic function.
- Two reference datasets, kept separate: `institutions` (identity, Open Finance identifier, financial conglomerate, FGC participation), living in `packages/core` reference data next to the FGC constants and used by ledger and reserve to compute FGC headroom per CPF per conglomerate. The conglomerate is the Central Bank's _financial conglomerate_ as published in IF.data, because the FGC regulation sums credits per "conglomerado financeiro"; an institution's guarantee is either FGC per conglomerate or FGCoop per associated cooperative (Sicoob), and a payment institution holding the account is recorded as such because it is not an FGC member; and `bank-profiles` (the scored criteria above), used by banking intelligence only. This keeps `reserve` from depending on `banking-intel`.

## Consequences

- Every profile change is a reviewed diff with sources, which is the audit trail. The agent that changes the data verifies each fact against a primary source where one exists and records the URL, the date checked and what was read; a fact that rests only on a secondary source is labelled as such. The owner's approval before merge is no longer required (waived by the owner on 2026-10-02, #21): an error found later is fixed by another pull request. A research job that proposes profile updates is a later ticket.
- The household-facing "last reviewed" date comes straight from the data, so stale evidence is visible, not hidden.

## Amendment 2026-10-02 (#23): how the comparison is computed

- An institution's score is the mean of its evidenced criterion scores weighted by the household's weights, rounded half up to an integer from 0 to 100; the ranking compares the exact means, and ties keep the dataset's order. A weighted criterion with insufficient evidence is left out of the mean and named on screen, never replaced by a guess.
- Weights are integers from 0 ("não conta") to 5, defaults in `packages/core` (fees 5; security, lock-in and public reviews 4; investment access and app quality 3; card benefits 2). A household stores its set in `bank_criteria_weights`; only the owner or an admin changes or resets it, and at least one weight must be above zero.
- Candidates are the top three scored institutions the household does not use. A pro or a con is a weighted criterion where the candidate is at least 10 points above or below the best score the household's own institutions reach on it.
- The institutions a household uses are inferred at read time from the institution names of the connections behind its accounts (`matchInstitutionByLabel`, shared with the reserve ranking); nothing is stored. Unrecognised names are shown so their owner can rename the connection. A household with no recognised institution is compared with the lower median of each criterion across all profiles.

## Amendment 2026-10-10: every reviewed institution is shown

- Besides the candidates, the comparison returns every profiled institution in score order, under the same weights and tie rule. The Bancos page lists them under "Todos os bancos avaliados" with place, score and review date, marking the household's own institutions and the candidates; it replaces the separate list of the household's institutions. A bank that ranks below the top three (Itaú and Bradesco under the default weights) was otherwise invisible to a household that does not use it. An institution without a score is listed last, without a place.

## Amendment 2026-10-14: Dinheiro a dois, essential and required weights, adjustable comparison settings

- Eighth criterion, `jointBanking` ("Dinheiro a dois", help "conta conjunta ou conta compartilhada para os dois"): 100 if the bank opens a PF joint deposit account for new customers (branch-only opening counts), 65 for a shared-access product (a procurador/representante, or a shared balance) without a true joint deposit account, 30 if joint holding is offered only for investment accounts, 0 otherwise. Scored and cited the same way as the other seven, `reviewedAt: "2026-10-13"`.
- A criterion's weight is now a level, not a bare 0-5 integer: `0` (não conta) through `5` (muito alto), or one of two special levels, `essential` or `required`. Together, every essential-or-required criterion accounts for exactly half the note, split equally among them, however many there are of each (each one individually pulls as hard as every numeric criterion combined; see effective weights below). They differ only in whether the criterion also gates candidacy: `essential` is a weight only, no gate; `required` additionally carries the household's minimum score for that criterion (default 60, 100 for `jointBanking`, step 5, `bank_criteria_weights.options`) and a bank that does not reach it is never a candidate. Essential exists for a criterion the household wants to dominate the note without being an all-or-nothing filter; required is for a hard line.
- Effective weights, computed in `packages/core` before scoring: let E be the count of essential-or-required criteria and N the sum of the remaining numeric levels. If E is zero, nothing changes from the previous scheme. If E is more than zero, every numeric criterion's effective weight is scaled by E (so the numeric group's total stays N×E) and every essential-or-required criterion gets an effective weight of N (or 1 if N is zero), which makes the essential-or-required group's total exactly N×E as well — essential and required criteria always carry, in aggregate, exactly half the note, whether or not they also gate. `jointBanking` defaults to `essential`, unchanged for the other seven.
- Only a required criterion gates: a bank meets it only if it has a score for that criterion and that score is at or above the household's minimum; an essential criterion carries weight but never excludes a bank on its own. A bank that fails a required criterion keeps its weighted score (so the full "todos os bancos avaliados" list stays informative) but is never a candidate, and the comparison records which required criteria it failed as `unmetRequirements`. The "todos os bancos avaliados" order changes accordingly: banks that meet every required criterion first (by score), then banks missing one or more (by score), unscored banks last.
- Two more household settings, alongside weights and minimums, both sliders on the Bancos page: `candidateCount` (1 to 5 institutions, default 3, was a fixed three) and `proConMinDifference` (5 to 30 points, step 5, default 10, was a fixed ten) — the gap a weighted criterion needs, against the best or worst of the household's own institutions, to count as a pro or a con. All three settings live in the same household-scoped row as weights (`bank_criteria_weights.options`, additive jsonb column), validated with the same per-field fallback to the product default as weights.
- If no profiled institution meets every required criterion, the Bancos headline says so ("Nenhum banco atende aos critérios obrigatórios da casa.") instead of naming a top candidate, and the candidates list is empty. A household with no required criterion (the product default, since `jointBanking` ships essential, not required) never sees this: every scored bank is eligible.
- `compareBanks` (`packages/core`) takes the household's weight levels and comparison settings directly and derives both the effective weights and the required-criteria gate from them itself, so a caller can never pass a required criterion that disagrees with the levels it came from.

## Amendment 2026-10-14 (bank page and household corrections)

- Every profiled institution has its own page, `/bancos/<institutionId>`, linked from the candidates and from "Todos os bancos avaliados": the score, place and unmet requirements under the household's weights, the deposit guarantee, and for every criterion its score, weight, evidence, sources (host, primary or secondary, date checked) and review date. Each criterion now carries `summaryPtBr`, the evidence or reason in the shipped locale, required by the schema next to the English `evidence`/`reason`, which stay the review record; a data change updates both in the same diff.
- Profiles stay product data, changed only through pull requests. A household cannot edit them; it can put a **correction** on top (`bank_criterion_override`, household-scoped): its own integer score from 0 to 100 for one criterion of one institution, a required note (up to 500 characters) and an optional https source link. A correction replaces the reference score, and turns an insufficient-evidence criterion into a scored one, in that household's comparison only (`applyScoreOverrides`, `packages/core`, applied before `compareBanks`), so its Bancos page, the bank's page and the analyst's facts agree. Only the owner or an admin writes corrections, the same rule as weights; members see them. The link requirement of #104 (editing shared data needs a source) does not carry over: a correction changes nothing for any other household, and a household's own judgement ("the shared balance does not work for us") has no URL. The note is required instead.
- A reference update never overwrites a correction. The correction stores `base_reviewed_at`, the reference criterion's `reviewedAt` when the correction was saved, read by the server from the shipped data and never from the form. When the reference criterion's `reviewedAt` is later than that (`referenceRevisedSinceOverride`), the bank's page shows the newer review date and score and asks "Usar a do Feudo" (deletes the correction) or "Manter a nossa" (moves `base_reviewed_at` to the current review, which silences the question until the next review); the Bancos page names the banks with such a pending question.
- A row whose institution or criterion no longer exists in the reference data is skipped when read, with a count-only warning, never applied.
- Keeping the reference current: the research job this ADR deferred is a scheduled Claude routine, not an app feature, so it costs no API spend and needs no scraping from the app (several bank sites block automated reads). It follows `docs/runbooks/bank-data-refresh.md`, re-verifies each criterion against its sources and opens a pull request that changes only the data file, under the rules above; households see the new review dates, and corrected criteria get the question above.

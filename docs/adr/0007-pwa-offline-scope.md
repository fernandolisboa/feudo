# Offline means read-only: cached shell and last-known data, writes require network

Feudo is an installable PWA (web manifest plus a Serwist service worker) used mostly on desktop with occasional phone use, and every write it accepts (categorization, reserve marks, settings, sync triggers) must be authorized against the session's household on the server. Offline support is therefore read-only: the app shell and the last data each screen loaded are cached and shown with a clear "last updated" indicator, while any write is refused with a message until the network is back. No offline queue, no conflict resolution, no background sync; web push is a later ticket.

## Consequences

- Cached data is scoped to the signed-in user's browser and cleared on sign-out and on household switch, so a shared computer never shows another household's last-known data.
- Nothing financial is precomputed for offline beyond what the screen already rendered; the deterministic layer stays server-side and there is no second copy of the rules in the browser.

## Amendment 2026-10-04 (#28, #116): how the copies are kept and erased

- **What is kept.** The service worker keeps the last page the server rendered for each signed-in screen that shows data without needing the network: Visão geral, Transações, Reserva, Bancos, Casa, Categorias and Como usar, each under its full address (a filtered Transações is its own copy). They live in one Cache Storage cache, `feudo-offline-copies`, at most 32 pages. A copy is served for at most 24 hours (the privacy policy's limit) and an older one is deleted the next time Feudo opens on that device (every navigation runs the expiry), since nothing runs while the app is closed. Preferências, Conectar banco, the sign-in screens and every `/api/` route are never kept, and neither are RSC payloads or server-action responses. A redirect, an error or anything that is not an HTML page is never stored. Build assets (precached shell, `/_next/static`) are the only other caches; they hold nothing personal. The Serwist `defaultCache`, which kept every page and RSC payload of the origin for 24 hours (#116), is gone, and the new service worker deletes its caches when it activates.
- **How a copy is made.** Loading a screen as a page stores it on the way through (network first). An in-app navigation brings the screen as an RSC payload, which is not a page the browser can reopen, so the app shell then asks the service worker to fetch that screen's page once more and store it. That second read is recorded in the access log as the same access (ADR-0008 amendment of the same date).
- **Freshness.** Every page carries the instant the server rendered it, shown as "Última atualização: hoje, 10:32" in the household's time zone whenever the browser is offline, or when the page on screen was rendered more than ten minutes before it started loading (a copy served because the network failed even though the browser believes it is online); in that case "Atualizar" asks the server again. An in-app navigation that reached the server moves the time forward. The browser reloads the page by itself when it comes back online.
- **Writes.** Offline, every write is refused in the browser before it is sent: a form submission is stopped before React sees it (a search form marked `data-offline-read` saves nothing and goes through to a copy or the "Sem conexão" page), and actions run outside a form check the connection first and show their own failure message where they were triggered, also on screens without the shell. The shell, where present, shows "Nada foi salvo: você está sem conexão." Nothing is queued. A write that fails because the network dropped while the browser still believes it is online fails like any other unreachable request.
- **Erasing.** Copies are scoped to one person in one household. They are erased, together with any cache that is not a build asset, before sign-out (even when the sign-out itself cannot reach the server), before switching household, before requesting account deletion, and whenever a signed-out or household-less screen opens (`/entrar`, `/exclusao-agendada`, `/comecar`), which covers expiry, revocation from another device and leaving or losing one's last household. The clear runs in the page and in the service worker, which also drops the expiration metadata (it holds each copy's URL, search terms included) and refuses to store any page whose fetch began before the clear, so a render still in flight for the person leaving is never kept. The shell also remembers the person and household the copies belong to (`localStorage`); when the signed-in page belongs to another person or household, it erases them before keeping new ones, which covers removal from a household that was not the last one and anything else that changes the active household without the switcher.
- **Without a copy.** Offline, a screen that has no copy, or any other page, shows the precached "Sem conexão" page, which carries no data and offers to try again.

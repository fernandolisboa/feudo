# Bank data comes from each user's own Meu Pluggy credentials, behind a swappable provider interface

Open Finance data in Brazil is only reachable through a Bacen-authorized aggregator; Pluggy's commercial plan costs R$ 2,500/month minimum, Belvo's starts at US$ 1,000/month, and no hobby-friendly tier exists anywhere in the market (see `docs/research/2026-09-02-aggregator-alternatives.md`). Pluggy's free personal product, Meu Pluggy, gives an individual their own API credentials for their own accounts, free indefinitely, scoped per CPF. We therefore start with each user bringing their own Meu Pluggy credentials, keep the provider behind a small interface so it can be swapped, and gate each growth step on a legal and financial condition.

## Decision: three steps

1. **Now (owner's household)**. Each user creates their own Meu Pluggy account, connects their banks on Pluggy's own site, and pastes their personal client id and secret into Feudo through a guided wizard. Feudo stores those credentials encrypted (ADR-0008) and syncs each user's data with that user's credentials only. Feudo never pools several people's accounts under one credential, never uses the Pluggy Connect widget, and never sees a bank password. Bank connections therefore belong to the user, not the household (ADR-0001).
2. **Closed beta (a handful of households)**. Stays on the same model only after **written confirmation from Pluggy support** that several people, each with their own Meu Pluggy account, each plugging their own credentials into a shared, unsold app, is personal use under their terms. Pluggy's FAQ draws the commercial line at "serving customers, connecting several CPFs' accounts, or turning it into a commercial product"; its terms PDF is silent on the scenario, so FAQ copy is not enough. Without that confirmation the beta is limited to the owner's household.
3. **Public launch**. Requires a paid, regulated aggregator (Pluggy Dados, Belvo or equivalent) and paying customers to fund it. Opening registration (registration mode `open`, resolved as in ADR-0001) is blocked by this gate and by the LGPD set in ADR-0008. Pluggy bills per API request above its plan minimum, so sync frequency is a cost lever, not just a freshness one.

OFX/CSV import is a backlog secondary source for institutions where a partner's account type makes Meu Pluggy impractical (for example C6 personal accounts export PDF only).

## Provider interface

The `sync` module talks to a `DataProvider`. `authenticate(credentials)` validates the pasted client id and secret against the provider and returns a `ProviderClient` scoped to that authentication; the client exposes `describeConnection`, needed because Pluggy has no endpoint listing a user's connections, so the wizard asks for one Item ID per connection and `describeConnection` is how Feudo learns which institution that Item ID belongs to (see CONTEXT.md, "Bank connection"), plus three reads: list accounts, list transactions since a date, list investment positions. The interface has no write: Feudo never asks the provider to re-read the bank. (Amended 2026-09-22, after the first production run: the original text also named a "refresh a connection" operation, implemented as Pluggy's `PATCH /items/{id}`. Pluggy rejects it with a 400 for a Meu Pluggy connection, because the item in the application is a proxy of an item living inside Meu Pluggy; Meu Pluggy refreshes the original every 24 hours for free, the proxy has no auto-sync of its own, and a manual update of a connector with MFA needs a token the user is not there to type. Feudo therefore reads the snapshot the provider already holds.) Every payload crossing that boundary is validated with Zod and normalized into two shapes, Feudo's own account and transaction, before anything else touches it; investment positions are accounts of type `investment`, not a third shape. Provider ids are kept only to deduplicate on the next sync. Pluggy's own category, counterpart document and investment rate fields feed the normalizer; nothing downstream knows the provider's field names.

**Normalized shapes.** Account: provider id, institution id, type (`checking | savings | credit_card | investment`), subtype or product type (for example CDB, LCI, LCA, poupança, Tesouro Selic, savings box), name, balance (integer centavos plus currency), holder document as a keyed hash (ADR-0008), and for investment types: rate, rate type (`percentage of CDI | fixed annual | inflation-linked | other`), due date, acquisition date (nullable, when the provider exposes one). Transaction: provider id, account id, date, amount, currency, description, provider category, type, counterpart type, counterpart document as a keyed hash (nullable).

Bank connections, provider credentials and synced accounts are owned by the `sync` module, which exposes assignment of an account to a household as a single operation; `households`, `ledger` and `reserve` never write these tables.

Sync runs automatically once a day and can be triggered manually up to three times per day per household, through Vercel Cron hitting bearer-protected route handlers, with no queue. The unit of work is the bank connection (user-owned); the daily job iterates connections, and a manual trigger from a household re-reads the connections whose accounts are assigned to it, counting against that household's quota. Feudo's cadence is therefore how often it reads, not how often the bank is read: that is Meu Pluggy's own daily refresh.

(Amended 2026-09-24: the daily sync job has a deadline. Route.ts owns the real limit (maxDuration, 60 seconds) and passes it down as runConnectionsSyncStep's budgetMs; the service reserves RUN_HEADROOM_MS (15 seconds) for the in-flight write and response. Before starting a connection the job checks the time left against MIN_CONNECTION_SLICE_MS (PROVIDER_REQUEST_TIMEOUT_MS, 15 seconds); a connection with less time than that is counted unreached and left untouched. Each connection gets its own abort signal, timed to at most half the run's total budget (maxConnectionSliceMs, derived from the deadline, not a hard-coded constant). Two new nullable columns on bank_connection (additive migration 0011_sync_connection_attempt_and_narrowing.sql) support this: last_sync_attempted_at, stamped through the scoped repository at the start of every attempt, before any provider call, from that connection's own reading of the run's clock rather than the run's one shared instant, so two connections attempted in the same run keep their real order; and first_sync_since, a sticky narrowing memory. listConnectionsToSync orders strictly by last_sync_attempted_at asc nulls first, created_at asc, so every connection rotates round-robin regardless of how its last attempt ended. Combined with the per-connection abort budget, a stuck connection costs at most half a run, not a whole turn that never comes. Credentials are decrypted once per user and cached for the run; authenticating happens fresh per connection against that connection's own signal, so its abort does not bleed into another connection's turn. A rejected secret (invalid_credentials) is also cached per user after the first authenticate call, so every other connection under the same user skips straight to the same status. A read cut short by its connection's abort is recorded too_slow when it got its full half-run slice and still did not finish (its own listing is the likely reason), or timed_out when the run itself was close to its deadline so the connection got less than its full slice (where it landed in the queue, not its own size). Both are distinct from a generic provider outage and neither write anything, resumable next run. An error other than ConnectionNotOwnedError raised while a connection is being attempted (a transient database failure, a bug in a provider implementation) is caught for that connection alone, counted failed and logged with the error's name and the connection id only; the run moves on to the next connection instead of coming back as one opaque failure for the whole job. A connection deleted mid-run (ConnectionNotOwnedError from the scoped repository) is counted gone; failure recording and failure counting happen in that order, so a delete racing the write is counted gone, never both gone and failed. syncAllConnections returns { ok, synced, failed, gone, unreached }; ok is false only when at least one connection was attempted and none of them synced. A run where everything was deleted or unreached is not red. Both provider paginators (getAllPages, getAllByCursor) throw ProviderListingTooLongError on reaching the page cap while the provider still offers more; the wizard's own first sync (establishConnection) retries once, narrowed to the previous month, before falling back to provider_unavailable, and persists that narrowed date as first_sync_since in the same transaction that creates the connection, so the daily job starts from it too rather than reverting to twelve months if the narrowed month turned out to have no transactions. The daily job records a too-long listing as its own status, listing_too_long, so it can be told apart from a generic outage. A first sync (no transactions in the ledger yet) that fails too_slow or listing_too_long sets first_sync_since to the previous month once, the first time it happens, if still unset. A lone timed_out does not, since on its own it says nothing about this connection's own size; two deadline aborts in a row — this run's timed_out following a too_slow or timed_out read off the row before this run's own outcome overwrites it — do narrow, since that pattern means the connection keeps losing its slice to something else in the queue rather than to its own history. first_sync_since is never reset once set; it simply stops being read once the connection has an actual synced transaction. A connection whose first sync is already narrowed and still comes back too_slow keeps failing visibly and rotating through the queue every run. Classification of the abort reason is derived from the slice the connection actually got (sliceMs === maxConnectionSliceMs) rather than raw time remaining, so the two never drift apart.)

## Considered options

- **Pluggy Dados or Belvo now**: the "correct" architecture, but R$ 2,500/month for one household. Rejected until step 3.
- **One Pluggy account for the whole app, users connect through the Connect widget**: the design CLAUDE.md originally assumed; it is exactly the multi-CPF pooling that Pluggy's terms define as commercial. Rejected.
- **Bank developer APIs**: Inter, BB, Bradesco and Itaú expose them only to business accounts; Nubank has none. Rejected.
- **OFX/CSV only**: free and aggregator-independent, but manual, inconsistent per bank and unavailable for several institutions. Kept as a secondary source, not the primary.

## Consequences

- The wizard must be honest with the user: they are handing Feudo a secret that can read all their accounts, and they can revoke it at Pluggy or delete it in Feudo at any time.
- End-to-end tests run against an in-repo fake `DataProvider` with Pluggy-shaped fixtures; Meu Pluggy has no sandbox, so the real provider is exercised by a manual smoke test on the owner's own credentials.
- A manual trigger from household A re-reads every connection with an account in A, so other households sharing one of those connections get an up-to-date read without spending their own quota; how fresh that read is still depends on Meu Pluggy's own daily refresh, not on the trigger. Accepted.
- CLAUDE.md's stack section (Connect widget, "MeuPluggy only for local development", billing per item) was aligned with this ADR in the same PR.

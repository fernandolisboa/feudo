# Auth runbook

Registration, verification and login run on Better Auth (`apps/web/src/modules/auth`), Drizzle
tables generated by the Better Auth CLI (`user`, `session`, `account`, `verification`,
`rate_limit`), plus the test-only `fake_sent_emails` table. The module's public surface is
`apps/web/src/modules/auth/index.ts`; `auth.ts`, `options.ts`, `service.ts`, `env.ts` and
`email/*` are private to the module — the one legitimate exception is the catch-all route handler
(`apps/web/src/app/api/auth/[...all]/route.ts`), which is the module's own HTTP entry point.

## Policy enforcement lives in Better Auth, not only in the server action

`REGISTRATION_MODE` and the terms-of-use acceptance are checked twice, on purpose:

- In `signUp` (`apps/web/src/modules/auth/service.ts`), for fast, no-round-trip feedback in the
  form.
- In a Better Auth `hooks.before` on `/sign-up/email` (`apps/web/src/modules/auth/options.ts`),
  which throws an `APIError` before any user is created. This is the layer that actually protects
  the system: it runs for every request to the route, including one that bypasses the server
  action entirely (a direct `POST /api/auth/sign-up/email`).

Because of this, `signUp`, `signIn`, `resendVerification` and `signOut` never call
`getAuth().api.*` directly — `auth.api.*` calls skip Better Auth's router-level rate limiter
entirely (it only runs in `onRequest`, which `auth.handler()` executes and `dispatchAuthEndpoint`
does not). Instead they build a `Request` and call `getAuth().handler(request)`, forwarding the
caller's headers so IP-based rate limiting sees the real request.

`nextCookies()` (the plugin in `options.ts`) only bridges `Set-Cookie` back onto Next's `cookies()`
for `auth.api.*` calls; it flags `auth.handler()`'s own dispatch as router-driven and skips it. So
the handler path in `service.ts` applies `response.headers.getSetCookie()` onto `cookies()` itself,
in one helper (`applyResponseCookies`) shared by `signUp`, `signIn` and `signOut` — outside a
Next.js request (e.g. a plain Vitest run), `cookies()` throws "outside a request scope" and the
helper treats that as a no-op rather than failing the call.

## Registration modes

`REGISTRATION_MODE` is read at request time (Zod-validated: `open | invite | closed`, default
`invite`, empty string treated as unset) by `readRegistrationMode`
(`apps/web/src/modules/auth/env.ts`) and enforced by `evaluateRegistrationMode`
(`packages/core/src/auth/registration-policy.ts`).

- `closed`: sign-up always refused.
- `invite`: sign-up refused unless the email holds a pending invite. **Invites do not exist yet**
  (ticket #11 adds them); until then, `signUp` always passes `hasPendingInvite: false`, so `invite`
  behaves exactly like `closed`. This is intentional, not a bug — do not "fix" it by defaulting to
  `open` before #11 ships.
- `open`: sign-up always allowed, subject to Better Auth's own validation and rate limits.

## Base URL and trusted origins

`readAuthBaseUrl` (`apps/web/src/modules/auth/env.ts`) prefers `BETTER_AUTH_URL`; when it is
unset (every Vercel Preview deployment, since the URL is unique per deployment) it falls back to
`https://${VERCEL_URL}`, and finally to `http://localhost:3000` for local development. The
resolved value is both Better Auth's `baseURL` and its sole `trustedOrigins` entry.

## Terms acceptance

`TERMS_VERSION` (`apps/web/src/modules/auth/terms.ts`) is a code constant, not an env var, until
there is a real terms/privacy document to version. Acceptance is **not** a separate table: `user`
carries `termsVersion` and `termsAcceptedAt` as Better Auth `additionalFields`, written in the
same `INSERT` as the user row. This also fixes a duplicate-sign-up crash: with
`requireEmailVerification` enabled, a duplicate email returns a synthetic user object instead of
throwing, and code that tried to write a second table keyed on that fake id would 500. Nothing
writes to a second table now, so a duplicate sign-up is a harmless generic `ok` response.

## Email sending

`EMAIL_PROVIDER` (`resend | fake`, default `resend`) selects the `EmailSender` implementation in
one place (`apps/web/src/modules/auth/email/select.ts`):

- `resend`: `ResendEmailSender` reads `RESEND_API_KEY`/`EMAIL_FROM` at send time and throws a typed
  error if either is missing — never at build or import time, so a preview without those vars still
  builds and boots; only sending an email fails, and `signUp` reports that failure as
  `sign_up_failed` rather than a false `ok`.
- `fake`: `FakeEmailSender` writes every message to the `fake_sent_emails` table
  (`apps/web/src/modules/auth/email/fake-email-repository.ts`) instead of an in-memory singleton.
  Vercel functions are separate processes, so a `globalThis` store would not be visible to the
  request that later reads it back through the test-only route; the database is. Used by
  integration tests and by Vercel Preview (`EMAIL_PROVIDER=fake`). Never written in production —
  see ADR-0008.

## Verification email content

Copy lives in `apps/web/src/modules/auth/strings.ts` (`verificationEmail`, with `{name}`/`{url}`
placeholders) and is rendered by `buildVerificationEmail`
(`apps/web/src/modules/auth/email/verification-email.ts`), which HTML-escapes the user's name and
the verification URL before embedding them in the HTML part. The name comes straight from the
sign-up form, so an attacker-chosen `<script>`-shaped name cannot inject markup into the email a
recipient opens.

## Test-only route

`GET /api/test-only/last-email?to=<email>` returns the last fake-sent message to that address as
JSON. It 404s unless `VERCEL_ENV !== "production"` **and** `EMAIL_PROVIDER=fake`, and separately
401s unless the request carries `authorization: Bearer <TEST_ONLY_TOKEN>`, compared with the same
constant-time helper the cron endpoint uses (`apps/web/src/lib/timing-safe-token.ts`). It never
exists in a `resend`-configured or production environment, so it never ships live traffic risk.
`TEST_ONLY_TOKEN` is a GitHub Actions secret and a Vercel Preview env var; it has no default and
the route refuses every request when it is unset.

## Running the E2E test

`apps/web/e2e/registration.spec.ts` drives a full sign-up → verify → sign-in → sign-out flow
through a real browser, reading the verification link from the test-only route above. `pnpm test`
stays unit-only; E2E runs in its own `e2e` CI job (`.github/workflows/ci.yml`), which:

1. Polls the GitHub deployments API for the PR head commit's Vercel "Preview" deployment until its
   latest status is `success`, reading `environment_url`.
2. Installs Chromium only in that job (`playwright install --with-deps chromium`).
3. Runs `playwright test` with `PLAYWRIGHT_BASE_URL` set to that URL; `playwright.config.ts` adds
   `x-vercel-protection-bypass`/`x-vercel-set-bypass-cookie` from `VERCEL_AUTOMATION_BYPASS_SECRET`
   and `authorization: Bearer $TEST_ONLY_TOKEN` to every request via `use.extraHTTPHeaders`.

To run it locally instead:

```
# against `pnpm --filter @feudo/web build && pnpm --filter @feudo/web start`
# with EMAIL_PROVIDER=fake, REGISTRATION_MODE=open and TEST_ONLY_TOKEN set in that server's environment
TEST_ONLY_TOKEN=<same value> pnpm --filter @feudo/web exec playwright test

# against a Vercel preview
PLAYWRIGHT_BASE_URL=https://<preview-url> TEST_ONLY_TOKEN=<value> VERCEL_AUTOMATION_BYPASS_SECRET=<value> \
  pnpm --filter @feudo/web exec playwright test
```

## Regenerating the Better Auth schema

`pnpm --filter @feudo/web db:auth-schema` runs the Better Auth CLI against
`src/modules/auth/auth.ts` and writes `src/db/schema/auth.ts`; review the diff (it does not know
about our naming or comment conventions) before running `db:generate` on top of it. The CLI needs
a reachable `DATABASE_URL` to introspect against, same as any other drizzle-kit command.

## Verification link expiry

`emailVerification.expiresIn` is `60 * 60` seconds (1 hour, `VERIFICATION_EXPIRES_IN_SECONDS` in
`options.ts`), matching ADR-0001. This is enforced by Better Auth itself; there is no
Feudo-specific test that mocks time past that window, since it would only be re-testing the
library's own configuration option.

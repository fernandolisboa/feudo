# Auth runbook

Registration, verification and login run on Better Auth (`apps/web/src/modules/auth`), Drizzle
tables generated by the Better Auth CLI (`user`, `session`, `account`, `verification`,
`rate_limit`), plus a hand-written `terms_acceptances` table.

## Registration modes

`REGISTRATION_MODE` is read at request time (Zod-validated: `open | invite | closed`, default
`invite`) by `readRegistrationMode` (`apps/web/src/modules/auth/env.ts`) and enforced by
`evaluateRegistrationMode` (`packages/core/src/auth/registration-policy.ts`) before any user is
created.

- `closed`: sign-up always refused.
- `invite`: sign-up refused unless the email holds a pending invite. **Invites do not exist yet**
  (ticket #11 adds them); until then, `signUp` (`apps/web/src/modules/auth/service.ts`) always
  passes `hasPendingInvite: false`, so `invite` behaves exactly like `closed`. This is intentional,
  not a bug — do not "fix" it by defaulting to `open` before #11 ships.
- `open`: sign-up always allowed, subject to Better Auth's own validation and rate limits.

## Email sending

`EMAIL_PROVIDER` (`resend | fake`, default `resend`) selects the `EmailSender` implementation in
one place (`apps/web/src/modules/auth/email/select.ts`):

- `resend`: `ResendEmailSender` reads `RESEND_API_KEY`/`EMAIL_FROM` at send time and throws a typed
  error if either is missing — never at build or import time, so a preview without those vars still
  builds and boots; only sending an email fails.
- `fake`: `fakeEmailSender`, an in-memory `FakeEmailSender` shared across the whole process via
  `globalThis` (Next.js compiles server actions and route handlers into separate module graphs, so
  a plain module-level singleton would not be the same instance across them). Used by integration
  tests and by Vercel Preview for now (`EMAIL_PROVIDER=fake`).

## Test-only route

`GET /api/test-only/last-email?to=<email>` returns the fake sender's last message to that address
as JSON, and 404s unless `EMAIL_PROVIDER=fake`. It never exists in a `resend`-configured
environment, so it never ships live traffic risk.

## Running the E2E test

`apps/web/e2e/registration.spec.ts` drives a full sign-up → verify → sign-in flow through a real
browser, reading the verification link from the test-only route above. `pnpm test:e2e` is not part
of CI; run it locally or against a deployed target:

```
# locally, against `pnpm --filter @feudo/web build && pnpm --filter @feudo/web start`
# with EMAIL_PROVIDER=fake and REGISTRATION_MODE=open in that server's environment
pnpm --filter @feudo/web exec playwright test e2e/registration.spec.ts

# against a Vercel preview
PLAYWRIGHT_BASE_URL=https://<preview-url> pnpm --filter @feudo/web exec playwright test e2e/registration.spec.ts
```

The target server needs `EMAIL_PROVIDER=fake` (so the test-only route is live) and
`REGISTRATION_MODE=open` (so sign-up is not refused); Preview deployments sit behind Vercel
Authentication, so requests need the `x-vercel-protection-bypass` header/token (see
`.claude/napkin.md`) unless bypass is configured for the run.

## Terms acceptance

`TERMS_VERSION` (`apps/web/src/modules/auth/terms.ts`) is a code constant, not an env var, until
there is a real terms/privacy document to version. `signUp` refuses registration (via
`evaluateTermsAcceptance`, `packages/core/src/auth/terms-policy.ts`) before creating any Better
Auth user unless the checkbox was checked, then writes a `terms_acceptances` row with that version
in the same call, before redirecting to `/verificar-email`.

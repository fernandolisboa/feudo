# Auth runbook

Registration, verification and login run on Better Auth (`apps/web/src/modules/auth`), Drizzle
tables generated by the Better Auth CLI (`user`, `session`, `account`, `verification`,
`rate_limit`, plus `organization`, `member` and `invitation` from the `organization` plugin, ADR-0001),
plus the test-only `fake_sent_emails` table. The module's public surface is
`apps/web/src/modules/auth/index.ts`; `auth.ts`, `options.ts`, `service.ts`, `env.ts`,
`invitations.ts`, `session.ts`, `cli.ts` and `email/*` are private to the module (`test/*` is a
test-only helper other modules import directly, not through the barrel — see
`test/signUpVerifiedUser.ts`). The two route handlers outside the module that need it — the
catch-all (`apps/web/src/app/api/auth/[...all]/route.ts`, the module's own HTTP entry point) and
the test-only mailbox route (`apps/web/src/app/api/test-only/last-email/route.ts`) — import only
from `apps/web/src/modules/auth/index.ts`, never from the module's internals directly.

The `organization` plugin is configured in `options.ts`, mapped onto household vocabulary by the
`households` module (`apps/web/src/modules/households`), which owns household creation, switching
and the `household_settings` table (name, time zone and reserve multiple live on the plugin's
`organization` row and this Feudo-owned table respectively). The dependency only ever runs one way,
`households → auth` (`households/service.ts` calls `getAuth()`, `households/scope.ts` takes an
`auth.CurrentSession`): `auth` never imports from `households`. `hasPendingInvitation`
(`apps/web/src/modules/auth/invitations.ts`) lives inside `auth`, not `households`, even though it
is a households-shaped concern, specifically to keep that direction one-way — it queries the
`invitation` table, which the `organization` plugin owns, so the query belongs next to the plugin
that owns the table it reads, not next to the module that gives that table its household meaning.

Two `organizationHooks` in `options.ts` write to Feudo-owned tables the plugin does not know about,
directly through Drizzle rather than through `households`, for the same reason:
`afterCreateOrganization` inserts a default `household_settings` row (overwritten by
`households.createHousehold` right after) so a raw `/organization/create` call can never leave a
household without one, and `afterRemoveMember`/`afterDeleteOrganization` null out
`session.active_organization_id` for every session that pointed at the household a user was just
removed from or that was just deleted. See `docs/runbooks/households.md` for the household side of
this (active-household resolution, single-owner enforcement, the isolation-test template).

## Policy enforcement lives in Better Auth, not in the server action

`REGISTRATION_MODE` and the terms-version match are enforced in exactly one place: a Better Auth
`hooks.before` on `/sign-up/email` (`apps/web/src/modules/auth/options.ts`), which throws an
`APIError` before any user is created. This is what actually protects the system — it runs for
every request to the route, including one that bypasses the server action entirely (a direct
`POST /api/auth/sign-up/email`). `signUp` (`apps/web/src/modules/auth/service.ts`) does not
re-check `REGISTRATION_MODE`; it only maps the hook's `APIError` message back to a typed
`SignUpOutcome`, and still short-circuits locally on the terms checkbox
(`input.termsAccepted`) for no-round-trip form feedback, since that flag never reaches the hook.

Because of this, `signUp`, `signIn`, `resendVerification` and `signOut` never call
`getAuth().api.*` directly — `auth.api.*` calls skip Better Auth's router-level rate limiter
entirely (it only runs in `onRequest`, which `auth.handler()` executes and `dispatchAuthEndpoint`
does not). Instead they build a `Request` and call `getAuth().handler(request)`, forwarding the
caller's headers so IP-based rate limiting sees the real request.

`nextCookies()` (the plugin in `options.ts`) only bridges `Set-Cookie` back onto Next's `cookies()`
for `auth.api.*` calls; it flags `auth.handler()`'s own dispatch as router-driven and skips it. So
the handler path in `service.ts` applies `response.headers.getSetCookie()` onto `cookies()` itself,
in one helper (`applyResponseCookies`) shared by `signUp`, `signIn` and `signOut` — outside a
Next.js request (e.g. a plain Vitest run), `cookies()` throws "outside a request scope" and the
helper treats that as a no-op rather than failing the call.

## Registration modes

`REGISTRATION_MODE` is read at request time (Zod-validated: `open | invite | closed`, default
`invite`, empty string treated as unset) by `readRegistrationMode`
(`apps/web/src/modules/auth/env.ts`) and enforced by `evaluateRegistrationMode`
(`packages/core/src/auth/registration-policy.ts`).

- `closed`: sign-up always refused.
- `invite`: sign-up refused unless the email holds a pending invitation. `hasPendingInvitation`
  (`apps/web/src/modules/auth/invitations.ts`) checks Better Auth's own `invitation` table
  (organization plugin, ADR-0001) for a row with that email, `status = "pending"` and an unexpired
  `expiresAt`, case-insensitively. The `hooks.before` hook (`options.ts`) only runs this query when
  `mode === "invite"`. **Creating an invitation is still ticket #11's job** — nothing in this repo
  writes a row to the `invitation` table yet, so in practice `invite` still behaves like `closed`
  until #11 ships the invite flow; the policy check itself is real, not a placeholder. Expired
  pending-invite rows are not purged anywhere yet — that cleanup also arrives with #11.
- `open`: sign-up always allowed, subject to Better Auth's own validation and rate limits.

## Base URL and trusted origins

`readAuthBaseUrl` (`apps/web/src/modules/auth/env.ts`) prefers `BETTER_AUTH_URL`; when it is
unset (every Vercel Preview deployment, since the URL is unique per deployment) it falls back to
`https://${VERCEL_URL}`, and finally to `http://localhost:3000` for local development. The
resolved value is both Better Auth's `baseURL` and its sole `trustedOrigins` entry.

Because `trustedOrigins` is a single per-deployment `VERCEL_URL` host, a Preview deployment is
only reachable through that exact deployment URL — a stable branch alias would fail Better Auth's
origin check — which is why the `e2e` CI job resolves and uses the deployment's own
`environment_url` rather than a branch alias.

## Terms acceptance

`TERMS_VERSION` (`apps/web/src/modules/auth/terms.ts`) is a code constant, not an env var, until
there is a real terms/privacy document to version. Acceptance is **not** a separate table: `user`
carries `termsVersion` and `termsAcceptedAt` as Better Auth `additionalFields`, written in the
same `INSERT` as the user row. This also fixes a duplicate-sign-up crash: with
`requireEmailVerification` enabled, a duplicate email returns a synthetic user object instead of
throwing, and code that tried to write a second table keyed on that fake id would 500. Nothing
writes to a second table now, so a duplicate sign-up is a harmless generic `ok` response.

`termsAcceptedAt` is `input: false` with a `defaultValue: () => new Date()` — the server clock
stamps it, never the client. Better Auth's sign-up body schema passes unknown keys through
unchanged, so a client-forged `termsAcceptedAt` still reaches the field parser; the `hooks.before`
on `/sign-up/email` deletes it from `ctx.body` before that parser runs, which is what forces the
`defaultValue` to fire instead of either rejecting the request or (a bug in Better Auth 1.7.3's
`parseInputData`) storing the unevaluated `defaultValue` function itself.

## Email sending

`EMAIL_PROVIDER` (`resend | fake`, default `resend`) selects the `EmailSender` implementation in
one place (`apps/web/src/modules/auth/email/select.ts`):

- `resend`: `getEmailSender` (`email/select.ts`) builds `ResendEmailSender` eagerly and its
  constructor throws a typed error (`MissingResendApiKeyError` / `MissingEmailFromError`) if
  `RESEND_API_KEY`/`EMAIL_FROM` is missing. `buildAuthOptions` calls `getEmailSender` once, outside
  the `sendVerificationEmail` closure, specifically so that throw happens while `getAuth()` builds
  its (cached) instance — the first request that touches auth — rather than inside
  `sendVerificationEmail`: Better Auth runs that callback through `runInBackgroundOrAwait`, which
  always logs a rejection as "Failed to run background task" and still reports the outer request
  `ok`, so a throw from inside it can never surface as a failed sign-up. A misconfigured `resend`
  provider now fails the very first request instead of silently accepting sign-ups it cannot verify.
- `fake`: `FakeEmailSender` writes every message to the `fake_sent_emails` table
  (`apps/web/src/modules/auth/email/fake-email-repository.ts`) instead of an in-memory singleton.
  Vercel functions are separate processes, so a `globalThis` store would not be visible to the
  request that later reads it back through the test-only route; the database is. Used by
  integration tests and by Vercel Preview (`EMAIL_PROVIDER=fake`). Never written in production —
  see ADR-0008.

## Verification email content

Copy lives in `apps/web/src/modules/auth/strings.ts` (`verificationEmail`, with `{name}`/`{url}`
placeholders) and is rendered by `buildVerificationEmail`
(`apps/web/src/modules/auth/email/verification-email.ts`), which HTML-escapes the user's name and
the verification URL before embedding them in the HTML part. The name comes straight from the
sign-up form, so an attacker-chosen `<script>`-shaped name cannot inject markup into the email a
recipient opens.

## Test-only route

`GET /api/test-only/last-email?to=<email>` returns the last fake-sent message to that address as
JSON. It 404s unless `VERCEL_ENV !== "production"` **and** `EMAIL_PROVIDER=fake`, and separately
401s unless the request carries `authorization: Bearer <TEST_ONLY_TOKEN>`, compared with the same
constant-time helper the cron endpoint uses (`apps/web/src/lib/timing-safe-token.ts`). It never
exists in a `resend`-configured or production environment, so it never ships live traffic risk.
`TEST_ONLY_TOKEN` is a GitHub Actions secret and a Vercel Preview env var; it has no default and
the route refuses every request when it is unset.

## Running the E2E test

`apps/web/e2e/registration.spec.ts` drives a full sign-up → verify → sign-in → sign-out flow
through a real browser, reading the verification link from the test-only route above. `pnpm test`
stays unit-only; E2E runs in its own `e2e` CI job (`.github/workflows/ci.yml`), which:

1. Polls the GitHub deployments API for the PR head commit's Vercel "Preview" deployment until its
   latest status is `success`, reading `environment_url`.
2. Installs Chromium only in that job (`playwright install --with-deps chromium`).
3. Runs `playwright test` with `PLAYWRIGHT_BASE_URL` set to that URL; `playwright.config.ts` adds
   `x-vercel-protection-bypass`/`x-vercel-set-bypass-cookie` from `VERCEL_AUTOMATION_BYPASS_SECRET`
   and `authorization: Bearer $TEST_ONLY_TOKEN` to every request via `use.extraHTTPHeaders`.

To run it locally instead:

```
# against `pnpm --filter @feudo/web build && pnpm --filter @feudo/web start`
# with EMAIL_PROVIDER=fake, REGISTRATION_MODE=open and TEST_ONLY_TOKEN set in that server's environment
TEST_ONLY_TOKEN=<same value> pnpm --filter @feudo/web exec playwright test

# against a Vercel preview
PLAYWRIGHT_BASE_URL=https://<preview-url> TEST_ONLY_TOKEN=<value> VERCEL_AUTOMATION_BYPASS_SECRET=<value> \
  pnpm --filter @feudo/web exec playwright test
```

## Regenerating the Better Auth schema

`pnpm --filter @feudo/web db:auth-schema` runs the Better Auth CLI against `cli.ts`
(`apps/web/src/modules/auth/cli.ts`, module-private — not part of `auth/index.ts`) and writes
`src/db/schema/auth.ts`; review the diff (it does not know about our naming or comment conventions
— it has, for example, dropped a hand-added `withTimezone: true` before) before running
`db:generate` on top of it.

The CLI needs a named `auth` export; `auth.ts` only exports the lazy `getAuth()` singleton on
purpose (docs/runbooks/auth.md above), so `cli.ts` builds a second, CLI-only `betterAuth` instance
from the same `buildAuthOptions`, with a placeholder Postgres connection string it never opens and
`EMAIL_PROVIDER` forced to `fake`. This is why `db:auth-schema` needs neither `DATABASE_URL` nor
`RESEND_API_KEY`/`EMAIL_FROM` to run, unlike `db:generate`, `db:migrate` and `db:check`, which do
need a reachable `DATABASE_URL`.

## Verification link expiry

`emailVerification.expiresIn` is `60 * 60` seconds (1 hour, `VERIFICATION_EXPIRES_IN_SECONDS` in
`options.ts`), matching ADR-0001. This is enforced by Better Auth itself; there is no
Feudo-specific test that mocks time past that window, since it would only be re-testing the
library's own configuration option.
